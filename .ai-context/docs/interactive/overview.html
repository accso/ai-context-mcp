1. The Problem

AI coding assistants (like GitHub Copilot) become much more useful when they understand your specific codebase. The obvious approach is to dump your source files directly into the conversation — but this breaks down quickly:

Without this system
  • Token budgets fill up fast — large repos get truncated
  • Irrelevant code is noise — the model has to work against it
  • Sending proprietary code to a cloud API is often not acceptable
  • Every query re-reads the whole project — slow
  • The assistant has no memory of what changed since last time
With this system
  • Only the relevant code sections are sent — an estimated 200–500 tokens per query (illustrative, not yet independently measured)
  • Answers are grounded in exactly the code that matters
  • Indexing and retrieval run on your machine — our tooling sends no data to external servers (the connected agent is a separate matter, see Privacy)
  • The index updates automatically as you edit files
  • Works across multiple projects / monorepos simultaneously

2. What This System Does

AI Context sits between your IDE and your codebase. It watches your files, builds a smart searchable index, and when your AI assistant asks a question, it finds and returns only the code snippets that actually answer that question — in far fewer tokens than a raw file dump.

Think of it like a local research assistant for your code. You ask "how does authentication work?" and instead of handing Copilot thousands of lines of source, it hands back raw ranked hits — file paths, line ranges, and a cached one-paragraph summary per file — no LLM condenses this into a single prose answer. Copilot then asks for the raw code from the specific locations it actually needs.

3. Key Benefits

⚡

Far Fewer Tokens Than a Raw Dump

Queries return raw ranked hits and cached per-file summaries (an estimated 200–500 tokens, not yet independently measured) instead of raw file dumps. You stay well within token budgets, even on large repos.

🔒

Local Indexing & Retrieval

All embedding, search, and summarisation runs on your own machine — embeddings + re-ranking via a bundled internal service, summarisation via a local LLM (LM Studio / omlx / Ollama). Our components send no source code to external services; what the connected agent does with returned context is outside our control (see Privacy).

🔄

Always Up-to-Date

A file watcher detects changes within 2 seconds of a save when native file events reach the container (see README's "File watching reliability" — a polling fallback covers setups, like some Docker Desktop/Rancher Desktop configurations, where they don't). Only the changed chunks are re-indexed. After a git pull, the system catches up automatically on next start.

🎯

Precise Symbol Lookup

Classes, functions, and interfaces are extracted using AST parsing and stored in a symbol index. The AI can look up exact identifiers directly — no fuzzy guessing required.

🗂️

Multi-Project / Monorepo

Each sub-project gets its own index. You can configure one project to automatically pull in context from another (e.g. a shared library) when relevant keywords appear in the query.

💻

Works With Any MCP Agent

The system speaks the MCP protocol over HTTP. Any coding agent that supports MCP — e.g. GitHub Copilot (native VS Code plugin or its IntelliJ plugin) or OpenCode — connects without extra integration work.

📖

Smart Documentation Search

Long docs (ADRs, wikis, RFCs) are indexed as a hierarchical table of contents. The AI navigates them by reasoning about structure — not just fuzzy similarity.

🧠

Hybrid Search Quality

Results combine semantic vector search (meaning) with token-level re-ranking (ColBERT). Exact class names and annotations surface reliably alongside conceptually similar code.

💾

Team-Friendly Backups

The vector index can be backed up as plain files committed to the repo (qdrant.vectors.json + postgres.json). Teammates who clone and run restore skip the full initial indexing — restore is a deliberate step (prompted by ai-context-up), not automatic on clone, and the committed backup covers projects/file_index/l1_summaries/l0_maps/doc_trees — not the symbol_index/import_edges/call_edges tables, which rebuild from a reindex.

4. How It Works (High Level)

The system has two separate phases: indexing (happening in the background) and retrieval (happening when you query).

Indexing — building the knowledge base

1
File Watcher monitors your project

A background process watches every source file for changes. When a file is saved it computes a SHA-256 hash. If the file hasn't changed, nothing happens — zero wasted work.

2
Smart Chunker splits the file

Changed files are split into meaningful chunks. Java, C#, TypeScript, and TSX files are split using real tree-sitter AST parsing at class/function boundaries; other languages (e.g. Kotlin, Python) currently use a regex-based structural fallback with the same boundary granularity; a SQL file is split at statement boundaries; a Markdown doc at headings. Each chunk is a coherent unit of code or text.

3
Embedder converts chunks to vectors

Each chunk is passed to a local embedding model (e.g. nomic-embed-text) which converts it into a 768-dimension numeric vector — a mathematical representation of its meaning.

4
Stored in Qdrant + PostgreSQL

Vectors go into Qdrant (the vector database). File metadata, structure maps, and LLM-generated file summaries go into PostgreSQL. Symbol locations (class names, function names) go into a dedicated symbol index table.

Retrieval — answering a query

1
IDE orients itself first

When you ask the agent something like "how does the payment flow work?", it first calls the repo_structure tool to get the project map and directory tree — no LLM round-trip, direct database lookup.

2
Agent calls semantic_search

The agent calls semantic_search(query) itself. If the query looks like a single identifier it resolves instantly via the symbol index; otherwise it falls back to hybrid/ColBERT vector search over Qdrant. No local LLM sits in this path.

3
Re-ranker improves result quality

The initial vector search returns ~20 candidates. A ColBERT re-ranker then re-scores them at the token level — ensuring exact class names and annotations rank highly, not just semantically similar prose.

4
Agent receives raw ranked results

semantic_search returns raw ranked hits — file path, line range, score, and an L1 summary where available (e.g. PaymentService.kt:45-120) — not a condensed prose summary. The agent judges relevance itself.

5
Agent fetches full content on demand

If the agent needs the actual source code, it calls get_file with the file path (and optionally a line range). The MCP server slices the stored chunk text (Qdrant) or doc-tree node body_text (PostgreSQL) to the exact requested lines, reports any coverage gaps, and never reads the project file from disk. No LLM needed, very fast.

6
Agent checks blast radius before a risky edit (optional)

Before changing a symbol, the agent can call analyze_impact(symbol_name, direction) to traverse the call/import graph (PostgreSQL) and get direct callers/callees, ambiguous call targets, and likely-covering test files — a heuristic, structural view (not a real language server).

7
Agent asks the real language server for certainty (optional)

When the heuristic call graph isn't precise enough, the agent can call resolve_symbol(file_path, line, character, kind) for a compiler-grade definition/references/hover answer from a real language server running in the LSP Bridge — available for languages auto-detected in that project.

5. The Three Retrieval Layers

Context is assembled from three levels of detail. The calling agent decides which levels to use based on which tool it calls — there is no LLM router in between.

Layer Name What it contains How it's built
L0 Project Map A static overview: which modules exist, where the entry points are, what the key files are. Covers the whole project in a compact form. Generated once at startup from the file structure. No LLM required.
L1 File Summaries A 4–6 sentence technical summary per source file. Answers "what does this file do and what are its key responsibilities?" Generated by the local LLM once per unique file version. Cached by content hash — never re-generated unless the file changes.
L2 Code Chunks The actual source code, split into AST-boundary chunks (class level, function level). Stored as semantic vectors in Qdrant. Chunked and embedded on every file change. Only changed chunks are re-embedded.

This layered approach means a high-level question ("what modules exist?") is answered cheaply from L0, while a precise question ("show me the JWT validation logic") goes all the way to L2 raw code.

6. A Query From Start to Finish

IDE (calling agent) │ │ "how does authentication work?" │ │ 1. repo_structure() → orientation ▼ MCP Server (:7100/mcp) │ │ 2. semantic_search("JwtValidator") │ identifier? → PostgreSQL symbol_index → exact hit │ else → embed query → Qdrant semantic search │ │ │ │ POST /rerank → ColBERT Re-ranker (optional) │ ▼ │ raw ranked hits + L1 summaries (no LLM, no prose) │ ← "## Search Results\n- auth/JwtValidator.kt:12-80 [score: 0.91]\n L1: Validates JWT signatures…" │ │ 3. get_file("auth/JwtValidator.kt", 12, 80) → only if step 2 wasn't enough ▼ MCP Server → Qdrant/PostgreSQL → exact source lines → calling agent

7. Main Components

ComponentWhat it isWhere it runs
File Watcher Monitors the project folder, detects changes, triggers chunking + embedding + summarisation. Also reconciles the index on startup to catch changes that happened while it was off. Docker container (Python)
MCP Server The HTTP endpoint your IDE connects to. Exposes 5 agent-facing tools: repo_structure, semantic_search, get_file, analyze_impact (call/import graph blast-radius traversal), resolve_symbol (real LSP definition/references/hover, for languages auto-detected in the project). A separate /mcp-admin endpoint exposes 2 operator-only diagnostics (list_recent_changes, get_index_status). Docker container (Node.js), one consolidated container per repo — one Express app per registered project inside it, each on its own port
LSP Bridge Runs real language servers (e.g. typescript-language-server, Python's multilspy-backed servers) in a lazy per-(project, language) process pool, idle-evicted after lsp.idle_timeout_minutes (default 15). Backs the resolve_symbol tool with compiler-grade certainty the heuristic call graph can't provide. Docker container (Python/FastAPI), one per repo
Inference Service Generates embeddings (nomic-embed-text-v1.5 via FastEmbed/onnxruntime) and, after Qdrant returns semantic candidates, re-ranks them at the token level (ColBERT MaxSim) so exact identifiers (class names, annotations) surface at the top. ~100–300 ms for 20 candidates. Mandatory, always-on — no torch, no LM Studio/omlx dependency for either. Docker container (shared, CPU-only)
Qdrant A vector database. Stores all the embedded code chunks (L2) and answers similarity queries: "find the 5 chunks most semantically similar to this query". Docker container (shared)
PostgreSQL Stores everything except vectors: file metadata, L0 project maps, L1 file summaries, documentation tree structures, the symbol index (class/function locations), and the call/import graph (call_edges, import_edges) backing analyze_impact and the [hub]/[bridge] structural-role tags on repo_structure. Docker container (shared)
Local LLM (LM Studio / omlx / Ollama) Runs on the developer's machine outside Docker. Generates L1 file summaries only — embeddings are handled by the internal Inference Service instead (see above), not this local LLM. There is no local LLM in the retrieval path — the calling agent is the only reasoning entity (see "Earlier Design: Routing LLM (Removed)" in the README). Host machine (not Docker)

8. Privacy & Local-Only Boundary

All of our processing happens on your machine. The inference service (embeddings + re-ranking), vector database, metadata store and MCP server run locally, and none of them send source code, summaries or query results to an external server.

Important boundary: we cannot control what the connected agent does with the context it requests. With a cloud-hosted model (e.g. GitHub Copilot, JetBrains AI Assistant), returned code excerpts become part of the agent's prompt and are sent to that provider, which may not count as local. Use an agent backed by a local or approved model if data must not leave your environment.

Our only external-to-Docker network call is to the LLM provider for L1 summaries (LM Studio / omlx / Ollama, local only if its base URL points to your machine) — embeddings and re-ranking stay entirely inside the Docker network via the bundled inference service. Your IDE connects to http://localhost:<port>/mcp — entirely local.
